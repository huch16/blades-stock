# 工具能力注册表改造方案（把「提示词驱动」收敛为「声明式」）

> 状态：**方案评审中，尚未动工**。本文只做设计与分期，落地需逐期确认。
>
> 承接：本文是「AI 模型解析唯一入口 + 运行记录」（`06b9589`）之后的**第二步**。
> 第一步解决的是「到底哪个模型在跑」；本文解决的是「到底给了模型哪些能力、
> 以及凭什么相信它会/不会用某个工具」。

---

## 一、结论先行（TL;DR）

**目标的不是"重写工具系统"，而是把已经存在但散落四处的机制收敛成单一事实源，并把"约束"从提示词升级为代码级闸门。**

现状其实已有半套声明式机制（`ToolGroup` / 关键词匹配 / 分组上限 / 核心白名单 / 按实测成功率重排），
但**同一件事的知识被复制在 5 张手工维护的表里**，且「严禁调用 X」这类纪律只写在提示词里、
不具约束力。因此：

| 收益 | 手段 |
|---|---|
| 加一个工具不会再漏登记（漏了就测试红） | 单一注册点 + 派生表一致性测试 |
| 「不要在这个流程里调 WebSearch」从"请求模型"变成"根本不给它" | 能力闸门（Capability Gate） |
| 每次请求实际注入了哪些能力，可查询、可复现 | 运行记录补 `tools_injected` |
| 同等问题下注入的工具数下降，且不再"凑数" | 按 token 预算而非按个数剪枝 |

**最重要的一句**：这一步**不会**重写 `AgentModeDirect/React/PlanExecute`、不会整体改提示词、
不会改 vendored 的 `blades.Tool` 接口。

## 三、问题定义（只针对这 4 个）

### P1 —— 工具元数据的源被复制成 5 份
新增一个工具的完整步骤是：写实现 → 在 `getToolsByQuestion` 里 append → 在 `toolGroupMap` 里登记分组 →
（可选）加进 `coreToolByGroup`。漏掉第 3 步 → 该工具变成第 3 条那样的"未映射"，
**既可能绕过 cap 常驻吃 token，也可能因未被任何组命中而完全不可达**。
没有任何测试能发现这两类错误。

### P2 —— 能力约束不可执行、行为不确定
「严禁调用 WebSearch」是写给模型的**请求**。模型可以遵守，也可以不遵守；
同一个问题这次调了、下次没调。更糟的是 `AgentModeDirect` 场景下我们真的不希望它联网，
却只能靠提示词碰运气。

### P3 —— 上限按"个数"而非按"成本"
`groupToolCaps` 按工具个数裁剪。68 个工具里可能一半是低频工具，
但只要不超过个数上限就全量进提示词。真正稀缺的是 **token**。

### P4 —— 无法回答"这次到底给了模型哪些能力"
运行记录（第一步成果）没有记注入的工具集。出问题时无法复现"模型当时能看到什么"。

## 四、目标与非目标

### 目标
- G1：工具能力有**单一注册点**，5 张表收敛为 1 张声明 + 派生校验
- G2：能力闸门是**代码级**的——"这个流程不得调用 X"由注入列表保证，不依赖模型自觉
- G3：注入预算从"个数"改为"**token 估算**"，同等问题下注入量下降
- G4：每次运行记录注入的工具集（组 + 数量 + 具体名称），可查询可复现
- G5：全过程**可灰度、可回滚**，任何阶段出问题能单独退回

### 非目标（明确不做）
- ❌ 不重写 `AgentModeDirect / React / PlanExecute` 三态编排
- ❌ 不整体重写提示词（只把**工具纪律类**条款迁移为闸门，其余不动）
- ❌ 不修改 vendored 的 `github.com/go-kratos/blades` 的 `Tool` 接口
- ❌ 不改变 `types.NewTool` 的既有调用方签名（42 处不动）
- ❌ 不引入新的第三方依赖

## 五、方案设计（分层）

### L0 能力声明单点

在 `backend/agent/types/` 引入能力声明（**扩展而非替换** `NewTool`）：

```go
// Capability 是一个工具能力的完整声明。构造即注册，单一入口。
type Capability struct {
    ID          string      // 工具名，全局唯一（注册表用它做键）
    Group       ToolGroup   // 归属能力组（用于闸门与预算）
    Tier        ToolTier    // core / extended / niche —— 剪枝时的优先级
    Description string      // 给模型看的描述（不变）
    Params      map[string]*ParamDef
    Handler     ToolFunc
    // 由谁提供：builtin（本仓库）/ mcp（外部服务器，运行时动态）
    Source ToolSource
}
```

注册表提供 `Register(caps ...Capability)` 与 `Registry()`，
并把 `toolGroupMap`、`coreToolByGroup`、`groupToolCaps` 的逻辑**改为从注册表派生**
（`toolGroupMap[name]` 这类查询保留为兼容访问器，避免一次性改 100 处调用）。

**关键约束**：`getToolsByQuestion` 不再维护 append 列表，改为
遍历注册表按 `Source==builtin` 取全部，MCP 工具仍按运行时动态注入。

### L1 派生表一致性测试（最高性价比，可独立交付）

新增测试，任何一条不满足即失败：
1. **每个内置工具都已注册到某个组** —— 直接消灭第 3 条那 20 个"未映射绕过 cap"的工具
2. **`coreToolByGroup` 里的名字都真实存在于该组** —— 防止白名单写错后静默失效
3. **注入列表无重名** —— 防止同一工具被注入两次
4. **分组上限内的工具总数 ≤ cap** —— cap 不再"名义存在实际失效"
5. **`Tool` 构造仍走 `types.NewTool`** —— 保证 schema 与 panic 保护不被绕过

> 仅这一层就能把"加工具漏登记"这类静默缺陷变成红灯，且**风险接近零**。

### L2 能力闸门（Capability Gate）

把"禁止在某流程调用某工具"从提示词迁移为代码：

```go
// Gate 决定一次请求实际可见的能力子集。
type Gate struct {
    // Forbid 这些组/工具在任何情况下都不可见（比提示词"严禁"强：根本不在列表里）
    ForbidGroups []ToolGroup
    ForbidTools  []string
    // Require 必须可见（用于技能声明的 tool_groups，行为对齐现状）
    RequireGroups []ToolGroup
}
```

应用位置：`getToolsByQuestion` 已经按组过滤，闸门只是在其后加一层确定性裁剪。

**迁移范围（仅工具纪律条款）**：把 `prompt_config.go` 里形如
「严禁调用 WebSearch」「不得调用外部搜索」的条款逐条转成对应流程的 `Gate`，
并从提示词中删除该句（提示词里保留**业务**纪律，如"必须用 GetMarketData 取一手数据"这类
正面指令——它描述的是流程，不是禁用什么工具）。

**灰度策略**：先"影子模式"——闸门计算结果只写日志、不实际裁剪；
对影子与实际的差异跑一段真实流量，确认不会误伤既有流程后再打开。

### L3 token 预算替代个数 cap

`groupToolCaps` 从 `map[ToolGroup]int` 演进为 `map[ToolGroup]tokenBudget`，
裁剪时按 `Tier` 优先（`core > extended > niche`），并累加"名称+描述+schema"的字符估算值，
超预算即停。**个数上限仍保留作为硬顶**，两者取先到者。

### L4 可观测（配套第一步的运行记录）

`AgentRunRecord` 增加一列 `tools_injected`（如 `base,stock_analysis|n=24`，
以及被闸门裁掉的 `gated_out=web_search`）。这样"模型当时能看到什么"可复现。

## 六、分期与交付顺序

| 阶段 | 内容 | 风险 | 可否独立回滚 | 预估 |
|---|---|---|---|---|
| **A** | L0 注册点 + L1 一致性测试 | 低（新增+测试，不改运行时行为） | ✅ 可 | 小 |
| **B** | 修掉 A 暴露的真实缺陷（20 个未映射工具归组/或显式声明为常驻） | 低 | ✅ 可 | 小 |
| **C** | L2 能力闸门（影子模式先行） | 中（会改变模型可见能力） | ✅ 可（配置开关一键退回） | 中 |
| **D** | L3 token 预算 + L4 运行记录补列 | 中 | ✅ 可 | 中 |

**建议顺序 A→B→C→D 逐期交付**，每期单独成 commit、单独过门禁。
C 是唯一可能改变模型行为的一期，必须影子模式验证后再打开。

## 七、风险与回滚

| 风险 | 影响 | 缓解 |
|---|---|---|
| **能力减少导致原本能跑通的流程失败**（最需警惕） | 模型少了某工具后无法完成任务 | ① C 期先影子模式对比差异 ② 闸门配置化，可一键全开 ③ 每次只迁移一类纪律条款，不一次性迁移 |
| 关键词误命中导致**过度注入**（现状已有） | token 浪费、模型分心 | L3 的 token 预算兜底；关键词表同时被 L1 测试约束"每条关键词至少映射一个真实工具" |
| 20 个未映射工具归组后**被 cap 裁掉** | 某些低频功能失效 | B 期逐个判定：真正低频的归入 `niche` tier 并给独立 cap；确实要常驻的显式声明 |
| MCP 动态工具与注册表冲突 | 回归 | MCP 工具始终走 `Source=mcp` 分支，不参与静态 cap，行为与现状一致 |
| 5 张表改派生时引入隐蔽行为变化 | 难排查 | 先加"派生结果 == 原硬编码表"的等价性测试，再删硬编码 |

## 八、验收标准（每期都要过）

1. `gofmt -l .` 空、`go build ./...`、`go vet ./...` 通过
2. 新增/受影响包的 `go test` 全绿；A 期起 L1 一致性测试为**必过项**
3. `npm run lint` 0 errors、`npm run build` 三道门禁通过
4. 冒烟自检 27/27
5. **实测对比**（而非断言）：同一组真实问题，改造前后注入工具数、命中组、
   令牌估算值可对比且方向符合预期
6. 运行记录可查到 `tools_injected`，与日志一致

## 九、需要你决策的三个点

1. **范围确认**：是否按 A→B→C→D 分期逐期交付？（我建议如此，而不是一次做完）
2. **C 期的纪律条款迁移范围**：我可以先只迁 3 条最典型的（如 `AgentModeDirect` 禁 WebSearch /

3. **B 期那 20 个未映射工具**：倾向"全部归组纳入 cap"（省 token，但可能裁掉低频能力），
   还是"逐个判定后声明式保留"？我倾向后者，但需要你确认哪些功能对你重要
   （例如基金 K 线、TDX 系列、MCP 管理类工具你是否在意模型能调用）。

## 十、一句话总结

现状已经有一套"半声明式"的工具选择机制，但知识被复制在 5 张手工表里、
约束只写在提示词中、预算按个数算。
本方案把它收敛成**单一注册点 + 代码级闸门 + token 预算 + 可观测**，
分四期交付，每期可独立回滚；唯一可能改变模型行为的是 C 期，
因此要求先影子模式验证。
